# Implementation Plan: 门店与订单对象授权

**Feature**: [spec.md](spec.md)  
**Date**: 2026-11-07  
**Status**: 本地实施与验证完成（2026-11-10）

## 技术上下文与设计

- 当前 Node.js HTTP/SQLite 项目将订单、备货、合同、鉴定、照片和提醒分在 `src/server.mjs`、`src/fulfillment.mjs`、`src/damage.mjs` 等模块。列表虽按顾客本人过滤，却对员工、经理、经营和管理员返回最近 150 笔所有门店订单；部分领域函数只核角色，未核订单门店。
- 先建立统一的订单对象授权判断（顾客本人、自店员工/经理、跨店接收、汇总角色），供各业务入口复用；跨店接收使用独立最小投影，避免先生成完整详情再删字段。
- 员工/经理列表及提醒 SQL 按其当前 `store_id` 过滤；经营/管理员不访问订单明细或逐笔提醒，其提醒仅返回按门店和状态聚合的计数。所有由订单 ID 或关联对象 ID 间接进入的路径都再次核订单归属，防止枚举。管理员权限配置所需账号元数据由独立 UC 授权，不附带业务订单。
- 跨店接收需要完整订单号/取货码证明；查找、提交都复核服务器身份、订单状态与码，且将接收门店固定为当前员工所属店。请求中伪造其他 `returnStoreId` 一律拒绝。返回结果单独塑形，不复用完整 `orderDetail`。
- 页面根据新契约区分自店订单工作台、跨店归还入口和经营汇总；外店最小资料不缓存为全量订单。现有跨店归还及结算逻辑保留业务事实。
- 不增加业务表或迁移；已有订单、合同、金额和证据不改。部署前对运行数据库保留可恢复备份；测试使用隔离库。

## 宪章核对

1. **业务价值**：顾客隐私、门店履约、跨店接收与经营汇总在规约中分别定义；UC-07/09/15、NFR-01 和 ER/序列图须同步。
2. **金额真实**：不改报价、押金、合同与演示资金；外店接收不看费用和核价。
3. **库存一致**：逐件归还仍由服务端事务核单件、实还与所在门店；归属门店不因异店归还改变。
4. **最小权限**：直接、间接、列表、附件及打印路径都要审计；不凭页面隐藏代替服务端授权。
5. **可验证恢复**：权限拒绝无写入；两店/多角色自动测试与浏览器路径；历史数据无迁移，运行数据备份可验证。

## 验收与回退

- 用隔离数据库建立两店订单，覆盖员工/经理自店正例与外店反例、顾客本人正例、经营/管理员聚合提醒及拒绝逐笔详情、精确码跨店受理、错误码、重复/部分归还及改门店攻击。
- 对业务关键写入比较拒绝前后订单、单件、支付、审计数量；浏览器检查相关工作台不显示越权信息且可完成跨店归还。
- 同步 API 契约、用例规约、需求台账、设计需求 PDF 与覆盖审计；原本依赖全局订单列表的演示路径要改为各自授权数据源。
- 回退只回退代码与文档，不反向修改既有业务行；如曾产生跨店归还记录，保持真实接收事实和原门店归属，不删除历史。

## 明确不包含

真实支付/签章、正式隐私合规、临时跨店轮岗授权、经营奖金规则、云端发布及老师访问控制均不在本特性内。
