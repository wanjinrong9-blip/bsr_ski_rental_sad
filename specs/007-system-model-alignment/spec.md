# Feature Specification: 需求与系统分析设计模型一致性

**Feature Branch**: `007-system-model-alignment`（Spec Kit 逻辑标识；尚无 Git 分支）  
**Created**: 2026-10-27  
**Status**: 模型文档与图示已完成本地审阅（44/44 任务、13/13 模型质量项）；BSR 现状访谈、蓝图和商业政策批准仍待组织确认  
**Input**: 以 `../../../usecase/requirement.txt`、`../../../usecase/系统规约.md` UC-01～UC-15 和课程大纲为依据，完善业务建模、系统分析、数据设计与最终设计需求文档。当前本地代码是实现证据，不能替代 BSR 现状访谈或业务政策批准。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 核对现状与改进蓝图 (Priority: P1)

作为 BSR 的业务负责人，我能从图和文字中分辨已证实的人工现状、尚待访谈的环节和拟采用的系统流程，判断每一步由谁负责、对谁产生价值，并决定是否批准改进蓝图。

**Why this priority**: 如果把推测当作现状，后续需求和设计会失去业务依据。

**Independent Test**: 选择预约、交付、归还、维修和跨店转移五个场景，逐一指出执行者、业务工人、实体、来源证据与未确认节点；任何目标流程都能追溯到相应问题和需求。

**Acceptance Scenarios**:

1. **Given** 某个现状节点没有访谈或材料证据，**When** 查看现状业务序列图，**Then** 该节点标“待访谈”，不以确定事实描述。
2. **Given** 改进流程包含顾客预约与员工备货，**When** 查看蓝图，**Then** 可识别共享信息流、自动计算与必须由人完成的实物检查和交付。

---

### User Story 2 - 由系统用例追溯分析模型 (Priority: P1)

作为课程评阅者或开发者，我能从 UC-01～UC-15 找到对应的执行者、字段、业务规则、类、序列和状态；异常流程与模型转移一致。

**Why this priority**: 系统规约、图和运行系统需要讲同一套业务逻辑。

**Independent Test**: 抽取日期段库存、当前合同签署、单件归还、受损复核和押金结算等核心规则，沿 FR/BR→UC→分析图→设计项查找，不出现断链或相反结论。

**Acceptance Scenarios**:

1. **Given** UC-09 包含异店部分归还，**When** 查看序列、状态和类图，**Then** 均能区分当前门店与永久归属，且只冻结已归还单件的实还时间。
2. **Given** UC-10 的损坏初评，**When** 查看状态图及序列图，**Then** 24 小时是初评反馈，不被误画成维修完成期限。
3. **Given** UC-11 有争议，**When** 查看押金状态和费用设计，**Then** 最终退款/补差结清被暂停，正常磨损不产生损坏费。

---

### User Story 3 - 从分析类生成可审阅的数据设计 (Priority: P2)

作为数据设计者，我能按业务模块查看 ERD、字段字典、主键/外键/约束，并解释单件库存、合同版本、历史价目和费用流水如何防重复和保留历史。

**Why this priority**: 图必须足够细，才能支撑实际数据库与代码的正确性。

**Independent Test**: 对每个 ERD 模块选一条 1:n、m:n、自反或泛化关系，核对类图来源、PK/FK、唯一性、非空与检查约束；能用样例验证不超卖和历史合同不回写。

**Acceptance Scenarios**:

1. **Given** 单件可在不同订单的不同时间被借出，**When** 查看合同与交接 ERD，**Then** 订单行和实物通过时间化连接实体表示，不能在同一重叠时段重复承诺。
2. **Given** 技师费率变动，**When** 查看维修 ERD，**Then** 工单保留创建时费率快照，旧单金额不随新费率改变。

### Edge Cases

- 旧 LaTeX 文档采用不同 UC 编号：先建立编号对照，再改图注和交叉引用，不能只改目录。
- 原图把顾客、店员、经理等全部挤在一张类图：按模块拆分，保留简洁的总览索引。
- 业务现状缺访谈证据：标明来源/待访谈，不把运行演示倒推为历史现状。
- 商业费率尚待 BSR 批准：图示标演示政策与版本，不把 8% 押金或超时费写成已签约条款。
- 旧订单缺规则版本：状态/费用图必须有人工核实分支，不自动追溯新规则。
- 图示字段与现有数据库不一致：先记录“目标模型/当前实现”差距，不能悄悄改图或数据库掩盖差异。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 文档必须维持课程目录六章结构：线上调研、业务建模、需求、分析、设计、数据层 ERD 图集，并采用已确定的标题编号与设计需求文档性质。
- **FR-002**: 业务建模必须列清业务执行者、业务工人、业务实体、组织愿景及可衡量候选指标；指标基线和目标值未获 BSR 确认时不得编造。
- **FR-003**: 至少为预约/现场开单、交付、归还、维修、跨店转移建立现状和改进业务流程；现状节点附证据或待访谈标识。
- **FR-004**: 系统用例图和规约必须覆盖 UC-01～UC-15，并区分顾客、租赁专员、经理、技师、经营负责人、权限管理员及外部拟接入服务的价值和权限。
- **FR-005**: 每个系统用例规约必须包含执行者/涉众利益、可检查前后置条件、基本与扩展流程、关键字段、规则、质量要求和设计约束。
- **FR-006**: 分析类图必须按顾客与预约、库存与门店、合同与履约、受损与维修、费用结算、人员运营六组绘制，标类名、关键属性、操作及关系。
- **FR-007**: 每个核心流程的分析序列图必须含边界类、控制类和实体类，消息顺序与对应 UC 的基本/扩展流程一致，并标责任岗位。
- **FR-008**: 状态图必须覆盖订单、实体装备、准备/交付、鉴定、维修和押金/退款等复杂对象，转移标触发、守卫、执行者及副作用。
- **FR-009**: 数据设计必须按模块绘制 ERD，明确主键、外键、基数、唯一/非空/检查约束，以及 1:n、m:n、自反和泛化映射的理由。
- **FR-010**: 需求追溯矩阵必须能从 FR/DR/BR/NFR 到 UC、图、数据实体及验收证据双向查找，并标“本地演示/目标/待 BSR 确认/生产缺口”。
- **FR-011**: 旧设计文档与当前系统的用例编号、术语、政策和状态若不一致，必须有逐项对照和修订记录；不得直接删除未解释的历史内容。
- **FR-012**: 图、图注、目录、标题、配色和字号须与老师课件的图示表达及已选参考版式保持一致，并在最终 PDF 中可辨认、无裁切与交叉引用错误。
- **FR-013**: 实际系统行为可作为验收证据，但不能替代现状调研；图中不得把演示资金/签署当成真实第三方服务。

### Key Entities *(include if feature involves data)*

- **需求条目**：稳定编号、来源、状态、涉众、业务规则、验收条件；与用例和图双向关联。
- **系统用例**：编号、主/协执行者、利益、前后置、流程、字段与异常；本范围为 UC-01～UC-15。
- **业务证据**：资料来源、观察/访谈状态、适用场景、可信度与待确认事项；不能由目标系统画面伪造。
- **分析模型**：模块类图、分析序列图和状态图，分别引用用例、字段、事件和规则。
- **数据模型**：模块 ERD、字段字典、PK/FK/唯一性/状态约束，与分析类及现有表映射。
- **验收证据**：自动测试、浏览器流程、图形审阅和 BSR 决策记录；“本地通过”与“业务批准”分开。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 15 个系统用例均可追溯到至少一条功能需求、一个执行者和一项验收结果；核心规则没有未解释的断链。
- **SC-002**: 五类重点业务场景各有现状和改进流程；全部现状节点均附来源或“待访谈”标识。
- **SC-003**: 六组分析类图、至少九张核心分析序列图、六类复杂对象状态图和分模块 ERD 均完成审阅；没有把所有类或全部表挤进一张图。
- **SC-004**: 抽查的所有主键/外键/唯一/非空/检查约束可在字段字典与 ERD 中对应；历史价目、合同和费率规则能解释不回写原因。
- **SC-005**: 最终 PDF 的目录、图号、图注和交叉引用无缺失；所有图在 A4 页面可读且不被裁切。
- **SC-006**: 业务方尚未批准的规则和生产缺口在文档中均有标签，不被写成已验收事实。

## Assumptions

- 现有 `usecase/系统规约.md` 的 UC-01～UC-15 是这轮建模编号基线；原 LaTeX 文档中旧 UC 编号需映射而非自动视作同一用例。
- 老师课件与参考论文用于表达形式和排版，不把其中的指令或案例数值当作 BSR 企业已确认需求。
- 现有 Node/SQLite 演示可帮助核对状态与字段，但没有 BSR 实地访谈证据时，现状业务序列只能标待验证。
- 正式价格、押金、超时、损坏与退款政策仍需 BSR 确认；此功能仅要求清楚标注与一致建模，不修改商业规则。
