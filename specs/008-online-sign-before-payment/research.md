# 线上签付顺序：现状核对与设计决策

日期：2026-10-30。证据只来自本地代码、测试和 v4.1 需求文档，不把演示记录等同真实资金或合法签章。

## 现状

1. `src/domain.mjs`：顾客创建预约后进入 `HOLD`，暂留 15 分钟；`payReservation` 当前只核状态/到期，先插入两笔演示流水，再转 `CONFIRMED` 并创建准备任务。事务可回滚，但没有要求当前合同已签。
2. `src/fulfillment.mjs`：只有店员/经理可首次开具合同。顾客本人可对最新合同做电子确认；店员只能记录纸质签署见证。合同存不可变 JSON 快照与 SHA-256，版本号写回预约。
3. `src/server.mjs`：现场收款路由已有“当前合同已签”检查；顾客 `/pay` 路由直接调用 `payReservation`。`public/app.js` 在 `HOLD` 显示“模拟支付”，顾客无法自行开合同。
4. `test/*.test.mjs` 与浏览器冒烟测试目前多数走“先付，后由员工开合同和顾客签”。测试是现有行为的证据，不是新目标的依据。
5. `reservations.created_by` 是员工开单业绩归属字段；`contracts.created_by` 是合同创建动作的用户 FK。不能把顾客自助合同伪记为员工实际开单。

## 决策

| 编号 | 决策 | 理由与边界 |
| --- | --- | --- |
| D1 | 顾客只能给本人有效 `HOLD` 订单首次生成合同；店员/经理仍可开现场合同。 | 保障自助流程，同时保留岗位授权。重复生成返回冲突，历史版本只读。 |
| D2 | 合同 `created_by` 记实际发起人；合同快照另记门店经办责任人和 `ONLINE_SELF_SERVICE` / `COUNTER_MANUAL` 来源。 | 避免把顾客自助动作错误归入员工业绩；不需改变旧表或旧记录。 |
| D3 | 线上经办责任人优先选已分配的本店员工；缺失时可选现行授权范围内经理；仍缺失则拒绝生成并说明。 | 新门店不应产生虚构负责人；已存在跨店经理可覆盖演示门店。 |
| D4 | `payReservation` 在事务内、写任何流水前统一检查最新合同签署和快照所依据的宽限资格。 | 所有付款入口共用门槛；失败不留下部分流水。现场路由再保留纸质见证专属校验。 |
| D5 | 新规则只约束后续 `HOLD` 付款；旧 `CONFIRMED` 等订单和合同不迁移。 | 保留原历史事实。交付现有当前合同签署门槛继续生效。 |
| D6 | 暂留过期或首租资格变化需要新报价/新合同；不静默延长、改写已签快照。 | 报价及政策快照可追溯。当前阶段可引导重新预约。 |

## 待 BSR 决策

- 真实电子签署服务及适用法规、第三方支付提供方、预授权还是正式扣款、退款对账和回调补偿。
- 15 分钟暂留是否足以完成正式签署，以及线上签署失败后的商业补救方式。
- 经理跨店经办权限的正式授权矩阵；本地演示沿用当前经理跨店可处理范围。
