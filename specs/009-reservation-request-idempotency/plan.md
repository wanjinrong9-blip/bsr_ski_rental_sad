# Implementation Plan: 预约提交去重与安全重试

**Feature**: [spec.md](spec.md)  
**Date**: 2026-11-02  
**Status**: Implemented and locally verified  
**Constitution**: 遵循业务价值追溯、金额与规则快照真实性、单件库存一致、对象权限、可验证变更与数据可恢复五项原则。

## Technical Context

- 本地应用：Node.js 24 原生 HTTP、`node:sqlite` 同步事务、SQLite WAL、无运行期 npm 依赖；顾客与员工界面使用原生 JS。
- 新数据：`reservation_requests` 持久化去重映射；不修改 `reservations` 旧行，不迁移历史金额。升级采用 `CREATE TABLE IF NOT EXISTS`，外键和唯一约束在数据库层保证。
- 接口：两个创建端点读 `Idempotency-Key` 请求头。首次 201，重放 200，非法 400，缺失 428，同键不同负载 409。旧调用方需补请求头；这是有意的创建接口契约升级。
- 摘要：`sha256(stableCanonicalJson(input))`，对象键排序，数组顺序保留。请求标识与实际提交账号、渠道共同构成作用域。
- 事务：先查映射再重新报价；首次在同一 `BEGIN IMMEDIATE` 中创建预约、规则同意、请求映射、通知及审计。数据库唯一约束是并发兜底。
- 页面：顾客结账和员工现场开单把意向负载与随机标识暂存于 `sessionStorage`；请求返回成功后清除。网络错误可原样重试，不要求顾客重选装备。

## Constitution Check

1. UC-04 的提交前置、成功/失败后置、异常流程与 E-04 用同一术语；文档将准确区分“重放原订单”和“创建新订单”。
2. 订单、合同和费用快照不被重放修改；押金与租金仍以 NOK 计。
3. 同一意向最多一笔暂留；不同意向仍由原库存算法决定能否同时租。
4. 映射按实际账号隔离；服务端不凭请求标识查询或返回其他账号订单。
5. 修改运行数据库前保留可恢复副本；测试用隔离数据库覆盖重试、并发、冲突、历史和现场路径。

## Rollout and Recovery

1. 备份运行 SQLite；记录当前源文件摘要和测试基线。
2. 先写隔离回归，验证旧实现会生成两笔预约。
3. 加表与领域层去重，接通顾客、员工接口；迁移重复执行并验证旧记录。
4. 页面保留待提交键，配合按钮忙碌状态；用浏览器路径验证顾客和现场操作。
5. 更新 UC-04、FR-C07、追溯和设计需求文档中相关状态/验收描述；重编 PDF 后检查页面。
6. 如回退，先在副本恢复旧代码；新表可保留但旧客户端若无请求头可能重复下单，必须同时回退页面与接口。运行数据可从备份恢复。

## Boundaries

- 当前本地 SQLite 单进程下的事务与唯一约束可测；多实例部署、网络分区和生产监控待专项验收。
- 相同请求标识被有意重复用于另一笔意向时返回冲突；客户应发起新意向而非绕过冲突。
- 真实支付、退款、通知外部通道不在本功能内。
