# Feature Specification: 预约提交去重与安全重试

**Feature Branch**: `009-reservation-request-idempotency`（Spec Kit 逻辑标识；当前项目尚未初始化 Git）  
**Created**: 2026-11-02  
**Status**: Implemented and locally verified  
**Input**: `usecase/系统规约.md` UC-04 的“同一请求只生成一单”，`requirement.txt` 的预约重试约束，以及对当前 `createReservation` 每次调用均创建新暂留订单的代码审查。

## User Scenarios & Testing

### User Story 1 — 顾客在网络重试后找回同一订单 (P1)

顾客点击提交后，即使响应丢失、重复点击或刷新页面，也能用同一提交标识取得原预约，而不会再次占用装备。新订单仍按原有规则阅读、日期库存、NOK 报价和合同签署顺序执行。

**Independent test**: 同一顾客用同一提交标识、同一负载并发请求两次，得到相同订单 ID/编号；数据库只有一笔预约、一份规则同意与一条预约创建审计。

1. **Given** 首次请求成功但客户端未收到响应，**When** 原标识与原内容重发，**Then** 返回原订单及当前状态，标记为重放，不能刷新暂留到期时刻或合同金额。
2. **Given** 两个标签同时发出相同标识和内容，**When** 服务端处理，**Then** 仅一个请求新建订单，另一请求读取原订单；无库存双占。
3. **Given** 标识相同但门店、日期、装备、数量、技能自评或同意内容发生变化，**When** 重发，**Then** 返回冲突并提示重新发起新提交；不创建新订单。

### User Story 2 — 门店现场开单可安全重试 (P2)

门店租赁专员在现场网络波动时，可以找回刚才为指定顾客建立的订单。员工、目标顾客和来源渠道必须保持准确，重放不重复计员工业绩或通知。

**Independent test**: 员工给顾客现场开单，同标识重放只得到同一订单；换目标顾客或负载返回冲突；其他员工使用相同随机标识互不串单。

### User Story 3 — 历史与异常可解释 (P3)

历史预约没有提交标识记录，其数据与金额保持原值。缺失或非法标识明确拒绝，已取消、已付款或过期的原订单仍按实际状态返回，不把重放变成新暂留。

**Independent test**: 对已有数据库执行迁移两次，旧订单数、价格、合同摘要不变；重放已过期订单只返回原状态；跨账号同标识既不泄露订单也不冲突。

## Functional Requirements

- **FR-001**：顾客预约与员工现场开单的创建请求须提供不可预测的 `Idempotency-Key`；有效格式为 16–128 个 ASCII 字母、数字、点、下划线、冒号或连字符。缺失或格式错误时拒绝，不创建暂留。
- **FR-002**：系统按实际提交账号、渠道及标识隔离请求；同一组合只映射一笔预约。渠道为 `ONLINE` 或 `COUNTER`。现场目标顾客属于负载内容，不能作为实际提交人。
- **FR-003**：服务端以稳定规范化的请求内容摘要核对重放；同标识同内容返回原订单（HTTP 200、`replayed: true`），首次创建返回 HTTP 201；同标识不同内容返回 HTTP 409。
- **FR-004**：重放须在报价、库存和规则重新校验之前读取已有结果；不得延长暂留、更新快照、重复写同意/通知/审计或重复计员工开单。首个请求原子写预约及请求映射，事务失败两者都回滚。
- **FR-005**：页面在网络不确定时保留本次提交标识与原始负载，重试复用；顾客改动内容或新建另一笔意向时生成新标识。成功收到订单后清除待提交记录并进入该订单。
- **FR-006**：现场开单遵循同一规则；重放时不重复写 `COUNTER_ORDER_CREATED` 审计。管理员或其他顾客不能靠猜测标识访问别人订单。
- **FR-007**：新表迁移可重复执行；旧订单不回填伪造请求标识，不改历史合同、金额和规则同意。当前 SQLite 单机事务保证本地并发序列化，生产多实例能力另行验证。
- **FR-008**：页面应在提交期间禁止重复按钮动作，并在可恢复网络错误时提示“可重试同一提交”；冲突提示用户核对内容后重新发起，不能默默改为新订单。

## Key Entities

- `ReservationRequest`：实际提交账号 FK、渠道、请求标识、稳定负载 SHA-256、预约 FK、创建时刻；`(actor_id,channel,request_key)` 唯一，`reservation_id` 唯一。
- `Reservation`：原有预约与金额、规则同意、合同状态；历史行保持不变。

## Scope and Decisions

- 顾客与员工页面使用 `crypto.randomUUID()` 产生每次意向的标识；标识只在对应会话内保留。不同账号不能共用映射。
- 摘要基于请求体递归按对象键排序后的 JSON；数组顺序保留。与业务含义相同但数组顺序不同的请求视为不同负载，复用同标识时冲突。
- 取消或过期不释放原映射；要新预约必须产生新标识，以免失去重试结果的确定性。
- 本功能不新增真实支付，也不代替支付回调幂等；第三方交易仍是独立缺口。

## Success Criteria

- **SC-001**：同标识相同负载的并发或重试创建一笔订单、一次同意、一次预约创建审计，且到期时间不被延长。
- **SC-002**：同标识不同负载、非法/缺失标识、跨账号与跨渠道场景有可预测 HTTP 状态和不泄露的结果。
- **SC-003**：历史订单数量、金额及合同摘要在迁移前后不变；全套 Node 回归与浏览器关键路径通过。
