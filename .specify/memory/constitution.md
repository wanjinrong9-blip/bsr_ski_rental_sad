# BSR 滑雪租赁系统 Constitution

## Core Principles

### I. 业务价值与可追溯需求

每项新功能必须明确业务执行者、系统执行者、给谁创造什么价值，以及可检查的
前置条件、成功结果和异常分支。需求、业务规则、状态、字段、用例、分析模型、
数据库和验收测试之间必须能相互追溯；修改一个关键流程时，必须检查受影响的
设计需求文档、图和系统提示是否一致。现行业务事实、拟议蓝图与课程演示假设
必须分别标记，不得把推测写成 BSR 已确认的业务事实。理由：本项目既是运行系统，
也是系统分析与设计的课程交付物。

### II. 合同、金额与政策真实性

正式订单金额以 NOK 计量，其他定位货币只作明确标注的参考展示。价格、押金、
取消、超时和损坏规则必须有版本及订单/合同快照；新政策不得追溯改写已确认的
历史订单。租金、押金、损坏费、超时费、退款和补差必须分项呈现，计算必须可
复核且支持幂等处理。演示支付、退款、联系记录和电子确认不得宣称为真实资金
到账、有效电子签章或业务方批准政策；未接入第三方服务前必须保持演示标识。
改变费率或签署—付款顺序前，必须先写明 BSR 待批准事项及历史订单处理方式。
理由：错误的金额或真实性表述会直接损害顾客和门店的信任。

### III. 单件库存与跨店一致性

每件实体装备必须保持唯一、恒定的库存标识，并可追踪当前门店、归属门店、
可租状态、清洁状态、维修状态及逐件借还时间。日期区间库存、下单、备货和
交付必须由服务端重复校验，不能只依赖页面展示；已出借或隔离的实物不得被
再次交付。异店归还与永久调拨必须分别留痕，角色之间读取同一事实来源。
理由：多店扩张的前提是实物去向和订单承诺可同时成立。

### IV. 最小权限与顾客隐私

所有读取和写入都必须按角色及对象归属校验；顾客只能访问本人数据，承包技师
只能访问分配给自己的维修与鉴定资料。照片、联系方式、会话令牌和演示数据库
不得进入公开静态资源或未来公开仓库；操作日志应保留处理人和时间，但界面只
展示岗位所需信息。新增外部通知、支付或签署接口前，必须先界定数据流、授权
和保留期限。理由：预约资料与损坏证据同时包含个人信息和争议材料。

### V. 可验证变更与数据可恢复

改变业务规则、权限、合同、库存或数据库结构时，必须提供可重复的自动测试；
涉及多角色流程时，还必须验证真实浏览器路径或等效端到端路径。数据库迁移必须
可重复执行，保留旧订单语义，并在触及运行数据前准备可恢复备份及验证方式。
并发更新必须拒绝过期版本或使用其他可证明的冲突控制，不得静默覆盖同事记录。
验收结论必须区分“本地测试通过”和“真实业务/生产环境已验收”。理由：演示
质量不能靠视觉效果代替数据安全和流程正确性。

## 业务与技术边界

- 当前应用是 Node.js 24 原生 HTTP 服务与 SQLite 本地预览；这些是现状，
  不是对未来集中部署的永久技术禁令。计划更换架构时必须证明兼容性、迁移和
  多门店并发能力。
- 日期及排班解释使用 Europe/Oslo；正式订单记账使用 NOK。展示层的定位与
  货币换算不能悄悄修改合同金额。
- 顾客、门店租赁专员、门店运营经理、装备检修技师、经营负责人和权限管理员
  的职责必须清晰。岗位轮岗或扩大开单权限前，必须确认授权规则和审计要求。
- 实际支付服务商、合格电子签署、奖金比例、正式费率、负载目标和法律适用性
  尚未由 BSR 确认。规格中必须把这些列为待决事项，不能编造已批准的答案。
- 未获用户明确同意，不初始化或上传 GitHub 仓库，不发布服务或真实顾客数据。

## 需求到交付的质量门槛

1. 先核对现有实现与需求覆盖审计，选择边界明确、能单独验收的改动；不能将
   “补齐整个系统”当作一个不可测的功能规格。
2. 功能规格必须写执行者目标、正常及异常场景、可检查的业务规则、数据状态、
   权限、质量目标和明确的范围外事项；待 BSR 决策的内容应显式标记。
3. 实施计划必须复用现有模块边界，列出数据库迁移、历史兼容、回退办法、
   权限检查、跨角色同步和文档图示的影响。
4. 任务与实现必须覆盖正常、边界、取消、重复提交、并发及历史数据场景。
   完成前运行现有 Node 自动测试；变更到交互流程时运行隔离数据库的浏览器
   流程测试并检查关键页面。失败项不得隐去。
5. 交付时更新需求覆盖状态，清楚写明剩余缺口、演示限制、测试结果和用户需
   决策之处。GitHub 上传仍按用户最终确认执行。

## Governance

本文件是后续 Spec Kit 规格、计划与实现评审的项目级约束；若与用户的新明确要求
冲突，先说明影响并由用户决定，不暗中降低隐私、金额或库存安全门槛。每次修订
必须记录原因、受影响原则、迁移与测试影响，并按语义化版本升级：不兼容的原则
删除或重定义升 MAJOR，新增原则或实质扩展升 MINOR，仅澄清措辞升 PATCH。
首次制定为 1.0.0。每份功能规格、计划和最终验收都必须对照五项核心原则，
未满足时写明差距和后续责任，不得标记为已通过。
