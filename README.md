### 网页小程序码状态

网页扫码入口有 OFF、PAUSED、READY 三态。默认 OFF，PAUSED 明确停止提供图片；READY 凭据到期后请求时立即转 PAUSED；READY 仅限独立 SHOWCASE，且必须同时具备发布开关、与小程序身份服务一致的 AppID、完整 PNG、项目目录外的私有码文件和带 HMAC 的私有人工批准凭据。旧版“绝对路径 PNG 加确认开关”不再自动进入 READY。二维码和凭据不得放进公开目录或准备上传的项目包。

tools/attest-mini-entry.mjs 可在运营者已从微信平台核对真实码、首页场景和 AppID 后，为私有图片生成带摘要与期限的本地批准凭据。该 HMAC 只防止本地图片/配置被悄然替换，**不能证明微信签发了图片**。正式 AppID 已在本机项目详情核对，平台发布状态、真实手机扫码与场景仍须独立验收；目前没有执行批准工具或打开 READY。具体变量名和失败场景见 019 验证记录。

## 本地运行

需要 Node.js 24 或以上版本，无需安装第三方运行依赖。

```sh
node src/server.mjs
```

访问 http://127.0.0.1:4173 。登录页提供六种角色的演示入口。数据存储在 `data/bsr.sqlite`；升级会补充表结构并保留现有业务记录。

预览服务需保持启动它的终端窗口运行。若 Codex 桌面应用或其命令会话关闭，临时启动的服务也可能退出；需要持续预览时，请在自己的 PowerShell 终端进入本目录运行 `node src/server.mjs` 并保持终端打开。访问失败时可先运行 `Invoke-RestMethod http://127.0.0.1:4173/api/health` 检查服务，再按需重新启动。默认监听 `127.0.0.1`。

可配置 `HOST`、`PORT` 和 `BSR_DB_PATH`。本地预览只允许 `HOST=127.0.0.1`、`::1` 或 `localhost`（大小写不敏感）；端口须为 1–65535 的十进制整数。数据库路径不得位于 `public`，包括经现有符号链接或 Windows junction 指向该目录的路径。危险配置在打开数据库前非零退出，不建立监听；`public` 内指向外部私有文件的链接也不能被静态服务读取。演示密码为 `Demo123!`，仅用于本地种子账号。详见 [013 本地验证](specs/013-local-preview-startup-guard/quickstart.md)。

### 隔离的本机候选模式

014 增加与课程演示分开的候选运行用途。先准备**独立且不存在**的数据库文件路径、已存在的私有备份目录，以及覆盖回环主机的 TLS 证书与私钥；它们不能放在 `public` 或经链接指入该目录。设置 `BSR_RUN_MODE=candidate`、`BSR_DB_PATH`、`BSR_BACKUP_DIR`、`BSR_TLS_CERT_PATH`、`BSR_TLS_KEY_PATH`、`BSR_PUBLIC_ORIGIN=https://127.0.0.1:<端口>`，并把 `HOST` 和 `PORT` 设成对应回环地址与端口。先运行 `node tools/candidate-setup.mjs preflight`，确认只读结果为 `needs_init`；再运行 `node tools/candidate-setup.mjs init-admin`，在交互提示中输入非预置凭据；复检为 `ready` 后才运行 `node src/server.mjs`。详细步骤与实际测试边界见 [014 验收指南](specs/014-deployment-identity-isolation/quickstart.md)。

候选直接提供**本机 HTTPS**，没有演示账号/商品/订单，关闭顾客自助注册和恢复。后续账号由权限管理员受控开通；顾客及高权限岗位须记录线下核验依据，首次登录须改密。未批准的商品及价目不能预约；真实支付、合格电子签署、公开访问和生产容量尚未验收。不要把现有 `data/bsr.sqlite`、私有备份或演示密码用于候选初始化。

候选备份恢复使用 `node tools/candidate-restore.mjs --backup <私有备份文件> --manifest <对应清单>`。先停服务并设置完整候选环境、`BSR_RESTORE_OPERATOR` 和**不存在**的私有目标 `BSR_DB_PATH`；备份与同名清单须位于 `BSR_BACKUP_DIR`。命令验证哈希、完整性和候选来源，只发布到新目标，并撤销备份内的旧会话；遇到已有目标、演示备份或坏清单会拒绝。完整操作顺序见 [014 验收指南](specs/014-deployment-identity-isolation/quickstart.md)。

### 隔离的合成预览模式（018，本机完整模拟业务）

## 关键流程

- 线上签付：顾客提交预约后，在 15 分钟暂留期内生成并阅读当前合同，勾选本人电子确认后才能进行演示付款。门店现场订单由员工记录纸质签署见证后才可登记演示付款。无合同、未签、过期或重复付款由服务端拒绝；成功只建立一组租金/押金演示流水和一份备货任务。顾客自助合同记录本人为发起人，另列门店经办责任人，不计入员工开单业绩。合格电子签章与真实第三方支付尚未接入。
- 预约安全重试：顾客结账和员工现场开单均须用一次提交标识；同账号、渠道、标识和内容的重试返回原订单，改内容返回冲突。页面在网络响应丢失或刷新后显示“找回上次预约/现场订单”，原订单的暂留、报价、同意和审计不重复写入。旧订单保留原状；创建接口须带 `Idempotency-Key` 请求头，详见 [009 接口契约](specs/009-reservation-request-idempotency/contracts/create-reservation.md)。
- 暂留到期：15 分钟暂留到期后，订单列表、详情和安全重试统一显示“暂留已过期”，金额标为历史报价；顾客可带回原装备重新选择租期，已有购物车替换前会确认。原订单与合同快照保留，库存释放，签约、演示付款及自行取消均不能继续。到期状态按服务器时间读取计算，不改写原始订单行，详见 [010 读取契约](specs/010-expired-hold-visibility/contracts/effective-status.md)。
- 维修：待接单 → 检查诊断 → 维修中 / 等待配件 → 提交经理验收 → 验收入库或报废。经理可退回维修。提交前必须填写诊断、处理结果与工时，并通过四项安全检查；验收通过前库存保持隔离。
- 排班与考勤：所有非顾客角色均可打卡，时间由服务器按 Europe/Oslo 记录。每天一组上下班记录；重复打卡被拒绝。店员只看本人班次，经理只看所属店班次、员工名册及每日实际到岗、迟到和早退；可受派技师作为候选单列。经理不能编辑外店班次或安排外店员工。已有打卡的班次禁止改写。
- 同步：服务端通过 SSE 推送变更信号，页面重新读取当前角色可见的数据。断线自动重连，回到页面时重新校验；编辑中的表单会保留草稿，保存或关闭后再同步。
- 门店权限：店员、经理只读取和处理当前账号所属店订单及逐件库存；跨店库存协调只看按门店/状态聚合数量。备货、合同、鉴定、照片、收款和复核也逐项校验对象归属。经理价目、采购、调拨发送及排班写入限本店；目标店员工确认调拨接收。经营负责人和管理员只看按门店/状态聚合的订单提醒与库存，不见单笔顾客业务或逐件库存档案；管理员审计只返回安全配置元数据。无权与不存在的逐单对象统一拒绝，拒绝不写业务状态。
- 异店归还：接收店员工输入完整订单号或取货码，系统仅在租赁中且有未还单件时显示归还截止、库存编号、名称与尺码。提交时重验代码并以当前员工所属店为实际接收店；结果只显示本批回执。原门店继续负责合同、押金、损坏和超时结算。异店归还不改变实物永久归属。
- 并发：维修工单采用版本号检查，旧版本提交返回冲突，避免覆盖其他人的更新。库存的状态或门店变化均保留流水。
- 多角色预览：每个浏览器标签页使用自己的会话凭证，可以在不同标签页分别登录经理、店员与维修人员，验证跨角色联动。
- 日期优先预约：顾客先选择门店、起租日期与归还日期，再查看该区间各规格可订数量；新订单采用挪威当地 09:00 起租、归还日 16:00 前还件，后端复核防超卖。卡片中的雪山线条仅是轻量装饰。
- 超时结算：首次有效租赁免计前 2 小时；此后按每件日租金的 10%／开始的一小时计算，每连续 24 小时封顶一天日租金。按实际单件归还时刻冻结，超时与核定损坏费分列后抵扣押金；超押金只登记联系和补差凭证，不自动追缴。费率是待 BSR 批准的课程演示规则。
- 员工业绩：经理、经营负责人和管理员可按挪威年度查看已确认合同的开单归属与当前净租金；用于年度奖金讨论，不自动计算或发放奖金。
- 订单提醒：所有非顾客角色都有提醒中心、页面顶部待办条、导航与铃铛上的小红色感叹号。店员和经理只见本店订单逐笔待办，技师只见本人维修工单；经营负责人和管理员只见匿名门店/状态计数，可标记自己的汇总为已阅。新增表示尚未查看，未解决表示业务尚未闭环；正常租赁中的订单也会列入，优先关注单列逾期归还、超时取货和异常押金。逐笔查看或手动标记只清除本账号的新增待阅状态，不关闭业务或影响同事；完成、取消和失效暂留自动移出。店员/经理逐笔列表支持搜索、分页和本页批量已读；技师列表不含顾客身份、取货码或金额。
- 提醒同步：已读记录保存在 SQLite，刷新、重启与重新登录均保留。通过 SSE 更新提醒，多个角色标签页通过 SharedWorker 共用一条不含业务正文的连接，避免浏览器并发连接耗尽；不支持 SharedWorker 时降级为仅可见标签页建立连接，并在回到页面时重新校验。另有每分钟的到期校验；编辑或弹窗中的草稿不会被重绘，导航和顶部待办提示仍可独立更新。维修重新分配、安排更新或经理退回后会重新提示，旧页面的已读操作不会吞掉后续新安排。普通业务通知有独立已读状态，不等于订单解决。

## 受损鉴定、押金与补差

下单前必须滚动阅读完整规则并主动勾选同意，才能核对并提交预约。服务端验证明确同意及规则版本，并保存规则快照与服务器时间；滚动到底只能说明界面已浏览至末尾，不能证明顾客实际理解了内容。新规则不自动追溯适用于历史订单。

受损分为无损 / 正常磨损、轻微、中度、严重、不可修复五档。等级用于描述损伤，不直接当作罚款比例。无损及正常磨损收费为零；可修复损坏按技师评估的工时加材料 / 配件费用计算，以有依据的折旧后重置估值为上限；不可修复按折旧后重置估值计算。费用均为整数 NOK。所有规则和估值均为课程演示，不代表 BSR 实际已批准的商业收费标准。

1. 店员逐件归还验收，只记录完好、需清洁或疑似损坏，不直接定价。任一疑似损坏都隔离装备并暂停自动退押金，包括尚未确定金额的情形。
2. 系统按受损单件创建鉴定单并关联维修工单。负责的技师进入“受损鉴定”，上传对应部位照片，填写分级、事实依据、成本和折旧估值。草稿可保存；提交前至少一张照片。照片上传后保留证据记录，提交后锁定；经理可退回补充，历史版本不会覆盖。
3. 经理逐件复核，全部受损件核定后在订单中单独确认费用结算。鉴定核定不等于维修安全验收，不会恢复库存。历史异常单无本版规则同意记录时，须先记录顾客沟通确认，再人工结算。
4. 核定费用 = 损坏费 + 逐件超时费。抵扣押金 = min(核定费用, 押金)；可退押金 = max(押金 − 费用, 0)；需补差 = max(费用 − 押金, 0)。超押金订单保持“待补差”，进入未解决 / 优先提醒；不自动追加扣款。
5. 门店员工查看必要的顾客联系方式，记录电话、邮件或当面沟通结果。未联系成功或存在异议时不能结清。核实后分次登记补差金额与演示凭证，全部补齐后订单才完成。凭证幂等且有版本冲突检查，禁止多收或重复登记。程序只保存沟通记录，不会自动发送邮件、拨号或核验真实银行到账。

照片以受保护的 SQLite BLOB 保存，不放在 public 目录。客户只可看自己的订单，技师只可看本人负责的鉴定，未登录和无关账号不能读取。支持 JPEG / PNG / WebP，客户端缩放至长边 1600px 并重新编码去除原始照片定位元数据；服务端复核格式签名和尺寸，每张不超过 3 MB、每件最多 6 张。不得上传顾客证件、面部或无关个人信息。运行数据库、会话、照片和截图已由 `.gitignore` 排除在未来的代码仓库提交范围之外。
